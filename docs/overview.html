WebMCP Scout · product overview

Ask several web shops at once, get one ranked list

Some web shops publish WebMCP tools: functions such as search_product that an AI agent can call instead of clicking through the page. Scout calls only the tools you approved, on every shop you listed, and merges the answers into one list. Below is one real run: a user looks for soccer boots under 150 dollars in the desktop viewer.

What happens in one run

Scout does the same seven things for every shop. The numbers come from the run shown further down.

Open

Scout starts its own Chrome, with no window and an empty profile: none of your logins or cookies.

Each shop page tells Scout which tools it offers and which inputs each one takes.

8 + 5 tools

Only the tools you approved in sites.toml go on. A tool whose inputs changed since you approved it is blocked as well.

An AI model picks one tool and fills in its inputs. Code then checks them against what the tool accepts.

Just before the call, Scout reads the tool list again to make sure the tool is still the approved, read-only one.

Not trusted: anything a web page saysTool descriptions, inputs, results and product names come from the shop. They can appear in the answer, but they cannot change which tools may run, the rules, or which shops are asked.
Trusted: your settings and Scout's codesites.toml lists the tools that may run. Price and stock limits are applied by code, not by the model.

Before the first run

You do this once. After that, everything happens in the viewer.

AApprove the tools

For each shop, list the tools Scout may call. The hash pins the tool's inputs: if the shop changes them, the tool is blocked until you check it and update the hash.

# sites.toml
[sites.sport]
url = "https://googlechromelabs.github.io/…"

[[sites.sport.capabilities]]
tool = "search_product"
schema_hash = "sha256:c8ae5f9e…"
class = "read_only"

BAdd a model key

Any OpenAI-compatible API works; this setup uses Groq. The key goes in .env, which git does not commit.

# .env (names from .env.example)
FALLBACK_BASE_URL=https://api.groq.com/openai/v1
FALLBACK_MODEL=qwen/qwen3.8-27b
FALLBACK_API_KEY=…

What Scout never does

These rules apply to every run, whatever a page or the model says.

✕Call a tool you did not list

Tools you did not approve, and approved tools whose inputs changed, are removed before the model is asked.

✕Change anything on a site

Only read-only tools run. Tools like add_to_cart and purchase_cart stay blocked.

✕Take orders from page text

Page text is treated as data. It cannot change your approved tools, the rules or the list of shops.

✕Use your browser profile

Each run gets a fresh temporary Chrome profile; Scout stops only the Chrome it started.

✕Let a model set the limits

Budget and stock filters are applied by code after the tool returns.

✕Render trace markup

HTML inside a trace is shown as text, and product URLs are not clickable.

How these screenshots were made: the viewer UI ran in Chrome (trunk serve) and was driven with Playwright. A small stand-in for the Tauri backend served two real scout ask traces recorded on 2026-09-29 and replayed the real output of a third run, the soccer-shoes request; the trace name in steps 2–3 follows the app's naming. The tampered trace in step 7 is test data. Orange callouts and the mouse pointer are an overlay drawn for the screenshots, not part of the app.
